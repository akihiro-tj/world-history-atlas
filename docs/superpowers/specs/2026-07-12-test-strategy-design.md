# テスト戦略 設計スペック

世界史マップのテスト戦略。AI がテストコードを書き、人間のレビューを仕様の判断に集中させる前提で、テストのレイヤ構成と E2E の運用（仕様の書き方・テストの生成・忠実性の保証）を定める。

- 作成日: 2026-07-12
- ステータス: ドラフト（レビュー待ち）

## 目的

1. 回帰検出の網を、人間がテストコードを読まなくても信頼できる形で維持する
2. 人間のレビューを「何を検証すべきか」（観点の完全性・期待挙動の正しさ）の判断に集中させる
3. テスト観点の抜け漏れを、勘ではなく手順で防ぐ。抜けは単発の機能ではなく、状態の組み合わせ（例: 解説パネルを開いたままフィルタを変える）と派生状態（他の状態から導出される表示）に潜む

## レイヤ構成（テスティングトロフィー）

| 層 | 実行環境 | 責務 |
| --- | --- | --- |
| unit | Vitest（純関数） | スキーマ・ロジック・変換の分岐と境界値 |
| component | Vitest + Testing Library（jsdom） | 画面骨格の統合・状態遷移・fetch 境界。地図はモック |
| E2E | 実ブラウザ（Playwright + playwright-bdd） | 実マップ・実レイアウト・実リロードの疎通と、クリティカルフローの担保 |

- **二重テスト禁止** — 同じ振る舞いを 2 層で検証しない（仕様変更のたびに両層を直すコストと、失敗時の切り分け困難を避ける）。どの層に置くかは次の「E2E の境界」で決め、E2E に置いた振る舞いは component に書かない。同じ機能の分岐・変形（エラーの種類別・境界値など）は component / unit に置く — これは二重ではなく粒度の分担
- **E2E の境界（2 つの基準）** — 次のいずれかに該当するシナリオを E2E に置く
  1. **技術基準**: 実 MapLibre の描画・実ビューポートのレイアウト・実ブラウザのリロード往復のいずれかを要する。MapLibre は jsdom で動かないため、地図の動線は E2E が唯一の防衛線になる
  2. **価値基準**: 壊れたら学習体験が成立しないコアフロー。技術的には下位層でも検証できるが、最も強い保証（人間レビュー済みの仕様 + 機械的束縛 + 実ブラウザ）の下に置くために E2E へ引き上げる。実行コストがあるため少数を明示して維持する
- MSW は使わない。バックエンドを持たない静的 JSON 取得のみのアプリで、fetch + parse + Result 変換は unit（`fetch.test.ts` / `manifest.test.ts`）が境界で網羅している

## E2E の運用（仕様駆動 BDD）

### 成果物と責務

| ファイル | 役割 | 人間のレビュー |
| --- | --- | --- |
| `e2e/features/*.feature` | 一次情報。観点カタログ＝実行される仕様 | 毎回（唯一の定常ゲート） |
| `e2e/GUIDELINE.md` | 観点の導出手順・書式・語彙の規約 | 内容を変えるときのみ |
| `e2e/steps/*.ts` | ステップ定義（シナリオ文 1 つに対応する部品） | 語彙が増減するときのみ |

### .feature の書き方

- Feature 冒頭のコメントに、その機能の**状態の軸**と、**E2E で扱わない観点とその担保先**を書く。観点の完全性レビューを「軸 × 組み合わせの表の空き」として構造的に行えるようにするため
- シナリオ文はステップ語彙のみで構成する。語彙にない文は `bddgen` が検出してエラーになるため、仕様と実装の対応は機械が検査する

```gherkin
Feature: 頻出度フィルタ
  # 軸: フィルタ = ★1のみ / ★1〜2 / すべて × 選択中 = なし / ★1都市 / ★2都市 / 地形
  # E2E で扱わない: 選択×フィルタの組み合わせ → component（App.test.tsx）で担保

  Scenario: フィルタで対象の頻出度だけが表示される
    ...
```

### 観点の導出（GUIDELINE.md の骨子）

AI が .feature を書く・更新するときは次に従う。

1. 対象機能の状態の軸（状態変数とその値域）を宣言する
2. 6 カテゴリを順に当てて観点を列挙する: ①状態の単体（loading / error / empty / success）②状態の組み合わせ（変更した状態 × 既存の状態）③派生状態の追従 ④境界値 ⑤エラー経路と回復 ⑥永続化・リロード
3. 各観点を E2E の境界（技術基準・価値基準）で判定し、E2E に置くものをシナリオ化する。置かないものは冒頭コメントに担保先とともに記録する
4. シナリオ文は `bddgen export` で得た既存語彙のみで書く

### 定常フロー（機能を追加・変更するたび）

1. AI が GUIDELINE に従い、該当する .feature を差分更新する
2. 人間が .feature の diff をレビューする（観点の抜け・期待挙動の正しさ）
3. CI で `bddgen`（語彙の機械検査）+ `playwright test` を実行する

新しい UI 操作が必要になったときだけステップ定義を追加し、その diff を人間が見る。

### 人間のレビューの 2 種類

- **(a) 仕様の判断** — .feature の diff。毎回発生する唯一の定常ゲート
- **(b) 部品の検収** — ステップ定義の diff。語彙が増減するときだけ発生する。見る点は 3 つ: 文と実装の意味が一致しているか / ロケータが正しい対象を指しているか / 否定形・待機の実装が適切か

(b) が残る理由: `bddgen` が保証するのは「文が語彙に存在すること」まで。部品の中身の正しさは機械では担保できず、部品 1 個の誤りはそれを使う全シナリオに波及する。

### 忠実性の設計（なぜ BDD か）

人間がテストコードを読まない前提では、信頼の根拠は「レビューされた仕様と実行されるコードの束縛の強さ」になる。Gherkin + ステップ定義は文と実装の機械的束縛を持ち、シナリオが何本に増えてもレビュー対象は部品数（10 個前後）に留まる。

採用しない代替:

- **plain Playwright + Markdown 仕様（Playwright Test Agents 型）** — 生成コードが仕様と一致することを検査する機構がない。自動修復（healer）はテストコードを書き換えて通すため、人間がコードを読まない前提では仕様の黙った弱体化を検知できない
- **仕様書と別に観点一覧の文書を持つ** — E2E の観点をステップ語彙で書いた時点で .feature と同一情報になり、二重管理が生まれる。軸と「扱わない観点」は .feature の冒頭コメントで足りる
- **生成コードの LLM 照合のみ** — 確率的な検査であり、機械的束縛の代替にならない

## E2E カタログ

E2E の境界の 2 基準で置くシナリオと、その理由。

| シナリオ | E2E である理由 |
| --- | --- |
| [smoke] 地図が表示される | MapLibre の起動。jsdom 不可 |
| テーマ選択でマーカーが表示される（直リンク含む） | 実マップ上のマーカー描画 |
| テーマ切替で前テーマのマーカーが消える | 実マップのマーカー入替 |
| マーカー／地形ラベルのクリックで解説パネルが開く | 実マーカーのクリック導線 |
| 頻出度フィルタで地図のマーカー表示が変わる | フィルタ結果の実マップ反映 |
| カラーテーマがリロード後も維持される | 実リロード + localStorage |
| データ取得失敗でエラーが表示され、再試行で回復する | 価値基準。データを表示できない学習アプリは成立しない |
| [mobile] ドロワーからテーマを選択してマーカーが表示される | モバイル実レイアウト + 実マップ |
| [mobile] 解説がボトムシートで表示される | 実ビューポートのレイアウト位置 |

E2E に置かない代表例と担保先: URL 反映・パネル開閉・不正な直リンクのフォールバック・データ取得失敗の変形（manifest 取得失敗など） → component（`App.test.tsx` ほか）。カラーテーマのトグルと OS 設定追従の DOM 反映 → component。フィルタの絞り込みロジック → unit（`filter.test.ts`）。エラー回復の代表フローは E2E に置くため、component には同じ振る舞いを書かない。

## unit / component の運用

- この層が受け持つのは「E2E に置かない振る舞い」: 同じ機能の分岐・変形、状態の組み合わせ（選択×フィルタなど）、カラーテーマの DOM 反映、純ロジック
- テストコードは PR でレビューするが、E2E のような束縛は持たない。保証が軽いことは設計上の受容で、その根拠はクリティカルなフローが E2E 側で人間レビュー済みの仕様と束縛の下にあること
