# 観点表フォーマット簡素化 設計スペック

`2026-07-13-test-strategy-design.md` で定めた「実行可能な観点表」の戦略はそのままに、**観点表の書式を簡素化する**。「観点表 = 実行される仕様（変換工程ゼロ）」という核は維持し、レビューで読む 1 行あたりの認知負荷を下げることだけを目的とする。

- 作成日: 2026-07-16
- ステータス: ドラフト（レビュー待ち）
- 前提: `2026-07-13-test-strategy-design.md`（本スペックは同ドキュメントの「観点表の書式」節を置き換える）

## 背景

現行の書式は、次の 2 つの機械機構を人間が読む表に持ち込んでいる。

1. **軸辞書 + 軸マトリクス表** — `check-specs` が直積網羅を機械検査するために、マトリクス表のセルには軸の**値**だけを書き（例: `★1のみ`）、実行フレーズは別の `## 軸` 表で解決する間接参照を入れている。このため「軸」という語が必要になり、`## 軸` セクション（全軸の辞書）とその中の `軸` カラム（行が属する軸）で同じ語が二重の粒度で現れる。
2. **層カラムによる実行判別** — 1 つの表に、実行される行（`c` / `e2e`）と実行されない文書行（`unit`・`直接` = 既存テストへのポインタ、`=N` = 同値、`対象外`）を混在させ、ランナーは `層` カラムで振り分ける。このため `層` が列にあるのにポインタ行だけを集めた `## unit` セクションも立ち、`unit` が「列の値」と「見出し」の両方に現れる。`c`（component の略）も辞書なしには読めない。

結果として、1 つの機能を読むのに「軸マトリクスと単発表の 2 形式」「値↔フレーズの間接参照」「7 列」「`=N` / `対象外` / `前置き` の記法群」を同時に把握する必要がある。人間が本当に読みたいのは「どの状態で・何をすると・どうなるか」だけである。

## 維持する前提

- **観点表 = 実行される仕様** — 表のセルはフレーズで書き、ランナーが 1 行 = 1 テストとして実行する。変換・生成の工程は持たない。
- **フレーズと実装の機械的束縛** — 語彙にないフレーズはテスト収集時にエラーになる。
- **二重テスト禁止**、**層の境界は技術基準のみ**。

## 新書式

すべての表を **1 形式・5 列**に統一する。軸マトリクス表・軸辞書・単発表の区別を廃止する。

| 観点 | 状態 | 操作 | 期待 | 層 |
| --- | --- | --- | --- | --- |

- **観点** — 行の一言ラベル。組み合わせ観点は `A × B` の組ラベルにする（人が目視で網羅を確認するため）。
- **状態 / 操作** — Given / When。フレーズを直接書く（`<br>` 区切り）。空欄可。値↔フレーズの間接参照はしない。
- **期待** — Then。フレーズ（`<br>` 区切り）。実行行は必須。
- **層** — 実行される層のみ: `e2e` / `e2e(smoke)` / `e2e(mobile)` / `結合`。

`前提:`（表全体の共通 Given）は表の直前に置き、繰り返しを避けるため残す。行ごとの追加準備は `状態` 列に直接書く（`前置き:` 記法は廃止）。実行順は 前提 → 状態 → 操作 → 期待。

### 廃止する要素

- `## 軸` セクションと値↔フレーズの辞書、軸マトリクス表
- `#`（連番）・`備考`・`=N`（同値行）・`前置き:` 記法
- 非実行の層値（`unit` / `直接` / `対象外`）を表に混ぜること

## 層の語彙

`層` カラムは「どこで走るか」だけを表す。

- `e2e` / `e2e(smoke)` / `e2e(mobile)` — 実ブラウザ（Playwright）。
- `結合` — 旧 `c`。実 App を jsdom で動かし、地図とデータ取得はモックする。

## 非実行情報の置き場

実行されない情報は表から出し、機能ファイル末尾の散文に分離する。

- `## 別層で検証` — 純ロジック等（旧 `unit` / `直接`）を「観点: ファイルパス」の箇条書きで参照する。
- `## 対象外` — テストしない観点とその理由を箇条書きで書く。

## 網羅性の扱い

直積網羅の**機械検査は手放す**。組み合わせの MECE は `観点` の `A × B` ラベルを人が目視で確認する。旧書式で `=N`（同値・非実行）として列挙していた行は、表からは省く（実際に走る行だけを書く）。同値の判断を残したい場合は散文に一言添える。

## 実例（頻出度フィルタ・before → after）

Before は `## 軸` 辞書 + 12 行のマトリクス（実行は 5 行、残り 7 行は `=4` の同値行）+ `## unit` セクション。After は実行行だけを直書きする。

```markdown
# 頻出度フィルタ

## 選択中のフィーチャー × フィルタ
前提: アプリを開いている<br>テーマ「古代オリエント」を選択している

| 観点 | 状態 | 操作 | 期待 | 層 |
| --- | --- | --- | --- | --- |
| なし × ★1のみ | | 頻出度フィルタを「★1のみ」に切り替える | 都市マーカー「バビロン」が表示されている<br>都市マーカー「ウル」が表示されていない | e2e |
| なし × ★1〜2 | | 頻出度フィルタを「★1〜2」に切り替える | 都市マーカー「ウル」が表示されている<br>都市マーカー「ウルク」が表示されていない | e2e |
| ★1都市を選択 | 都市マーカー「バビロン」を選択している | 頻出度フィルタを「★1のみ」に切り替える | 解説パネルに「バビロン」と表示されている | 結合 |
| ★2都市を選択 | 都市マーカー「ウル」を選択している | 頻出度フィルタを「★1のみ」に切り替える | 解説パネルが表示されていない<br>都市マーカー「ウル」が表示されていない | 結合 |

## テーマ切替との組み合わせ
前提: アプリを開いている<br>テーマ「古代オリエント」を選択している

| 観点 | 状態 | 操作 | 期待 | 層 |
| --- | --- | --- | --- | --- |
| 切替後もフィルタ維持 | | 頻出度フィルタを「★1のみ」に切り替える<br>テーマ「壊れたテーマ」を選択する<br>テーマ「古代オリエント」を選択する | 都市マーカー「バビロン」が表示されている<br>都市マーカー「ウル」が表示されていない | 結合 |

## 別層で検証
- 絞り込みの境界（importance 1/2/3）: `src/theme/filter.test.ts`
```

セルのフレーズ（文言）は既存の語彙をそのまま使う。変わるのは表の構造だけで、`e2e/steps/` と `tests/component-steps/` のフレーズ実装は変更しない。

## コード・ドキュメントの変更

- `tests/spec-runner/parse.ts` — 軸（`AxisValue` / `axes`）・マトリクスモード・`axisColumns`・`precondition`・`note` を撤去。`SpecRow` は `label` / `states` / `operations` / `expects` / `layer` に縮小。`rowPhrases` は 前提 + 状態 + 操作 + 期待 の連結、`rowLabel` は `観点`。
- `tests/component.spec.ts` / `e2e/catalog.spec.ts` — 層フィルタ `c` → `結合`。未定義フレーズで収集時に落ちる検査は維持。
- `scripts/check-specs.ts` — 直積網羅・軸・`=N`・マトリクスのセル値検査を撤去。残すのは ①`層` 値が既知集合に含まれる ②実行行に期待がある ③`## 別層で検証` のポインタ先ファイルが実在する、の 3 点のみ。
- `specs/GUIDELINE.md` / `CLAUDE.md`（specs 節）/ `README.md` — 新書式に更新（「表の書き分け」「表の書式」の軸ルールは消滅）。
- `specs/*.md` 7 本 — 新書式へ書き換え。

## 移行の実行体制

1. **メイン** — `parse.ts` / runner / `check-specs` を改修し、`importance-filter.md` を参照実装として書き換えてテストを green にする。GUIDELINE / CLAUDE.md / README を改訂する。
2. **subagent（sonnet・並列）** — 参照実装を雛形に、残り 6 本（`app-boot` / `color-theme` / `error-handling` / `feature-detail` / `mobile` / `theme-selection`）を書き換える。`=N` 行の取捨と観点ラベルの言い換えに軽い判断が要るため haiku ではなく sonnet。
3. **メイン** — 各書き換え後に `pnpm test` / `pnpm check-specs` / `pnpm typecheck` を実行し、統合する。

## 検証

- `pnpm test`（Vitest: spec-runner の parse unit + component 実行行）が green。
- `playwright test --list` が e2e 行を列挙でき、`pnpm e2e:smoke` が通る。
- `pnpm check-specs` が OK。
- `pnpm typecheck` / `pnpm lint` が通る。
