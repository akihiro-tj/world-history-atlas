# テスト戦略 設計スペック

世界史マップのテスト戦略。AI がテストコードを書き、人間のレビューを仕様の判断に集中させる前提で、テスト仕様を「実行可能な観点表」に一本化する。観点表は人間がレビューする唯一の一次情報であり、**そのまま実行される**（仕様からテストへの変換・生成の工程が存在しない）。

- 作成日: 2026-07-13
- ステータス: ドラフト（レビュー待ち）

## 目的

1. 回帰検出の網を、人間がテストコードを読まなくても信頼できる形で維持する
2. 人間のレビューを「何を検証すべきか」の判断に集中させる。全レイヤのテストケースの過不足を、観点表のレビューだけで確認できる状態を作る
3. テスト観点の抜け漏れを、勘ではなく状態変数の組み合わせを観点として並べることで防ぐ

## 基本原則

- **観点表 = 実行される仕様** — 観点表のセルはフレーズ（ステップ語彙）で書き、ランナーが表をパースして 1 行 = 1 テストとして実行する。レビューした成果物と実行される成果物が同一なので、変換の忠実性という問題がそもそも発生しない
- **フレーズと実装の機械的束縛** — 語彙にないフレーズはテスト収集時にエラーになる。信頼の土台はフレーズ実装（少数・安定）に集約され、行が何行に増えてもレビュー対象はフレーズ数に留まる
- **二重テスト禁止** — 同じ振る舞いを 2 層で検証しない
- **層の境界は技術基準のみ** — e2e = jsdom で原理的に検証できないもの（実 MapLibre の描画・実ビューポートのレイアウト・実ブラウザのリロード往復）/ 結合 = 実 App を jsdom で動かし地図とデータ取得をモックした結合でしか確認できないもの（画面の状態遷移・モジュール連携）。純ロジック等の非実行検証は既存の unit・直接テストへポインタで参照する
- MSW は使わない。静的 JSON 取得のみのアプリで、fetch 境界は unit が網羅している

## 成果物と配置

```
specs/
  GUIDELINE.md            観点導出・表の書式・フレーズ語彙の運用（全レイヤ対象）
  <機能>.md               実行可能な観点表（機能ごと 1 ファイル。唯一の一次情報）
tests/
  spec-runner/            表のパースとフレーズのディスパッチ（共有ライブラリ、純ロジック）
  component-steps/        component 用フレーズ実装（Testing Library + モック）
  component.spec.ts       Vitest エントリ（specs/*.md の 結合 行を実行）
e2e/
  steps/                  E2E 用フレーズ実装（Playwright）
  catalog.spec.ts         Playwright エントリ（specs/*.md の e2e 行を実行)
src/**/*.test.{ts,tsx}    unit・直接テスト（観点表からポインタで参照）
scripts/check-specs.ts    層・期待・ポインタの機械検査（CI）
```

playwright-bdd・Gherkin ランナーなどの外部フレームワークは使わない。ランナーは素の Playwright / Vitest の上の薄いパーサ + ディスパッチ（数百行）で、リポジトリが所有する。

## 観点表の書式

すべての表は 1 形式に統一し、**状態（Given）→ 操作（When）→ 期待（Then）を左から右に読む**。列の役割を見出しに書くことで「どう読むか」を表自体に持たせる。

| 観点 | 状態 | 操作 | 期待 | 層 |
| --- | --- | --- | --- | --- |

- **観点** — 行の一言ラベル。相互作用する状態変数の組み合わせは `A × B` の組ラベルにする
- **状態 / 操作** — Given / When。フレーズを直接書く（`<br>` 区切り）。空欄可
- **期待** — Then。フレーズ（`<br>` 区切り）。実行行では必須
- **層** — `e2e` / `e2e(smoke)` / `e2e(mobile)` / `結合`。実行される層だけを書く

表の直前の `前提: フレーズ<br>フレーズ` はその表の全行の先頭で実行される共通 Given。実行順は 前提 → 状態 → 操作 → 期待。結合 行はモックのフィクスチャを、e2e 行は実データを参照する。

### 非実行の検証は散文へ

表には実行行だけを書く。純ロジック等の非実行検証（既存の unit・直接テストへのポインタ）と、意図的にテストしない観点は、ファイル末尾の散文に分ける。

- `## 別層で検証` — `- 観点: `パス`` の箇条書き
- `## 対象外` — `- 観点: 理由` の箇条書き

### 例（頻出度フィルタ）

```markdown
## 選択中のフィーチャー × フィルタ
前提: アプリを開いている<br>テーマ「古代オリエント」を選択している

| 観点 | 状態 | 操作 | 期待 | 層 |
| --- | --- | --- | --- | --- |
| なし × ★1のみ | | 頻出度フィルタを「★1のみ」に切り替える | 都市マーカー「バビロン」が表示されている<br>都市マーカー「ウル」が表示されていない | e2e |
| ★1都市を選択 | 都市マーカー「バビロン」を選択している | 頻出度フィルタを「★1のみ」に切り替える | 解説パネルに「バビロン」と表示されている | 結合 |

## 別層で検証
- 絞り込みの境界（importance 1/2/3）: `src/theme/filter.test.ts`
```

各行は「この状態で（Given）→ この操作をすると（When）→ こうなる（Then）」と左から読める。相互作用する状態変数の組み合わせは観点の `A × B` ラベルを並べ、網羅（MECE）は人が観点の列を目視で確認する。

## 束縛と検査（忠実性の設計）

- **フレーズ ↔ 実装** — ランナーは登録済みフレーズ（正規表現）にマッチしないセルをテスト収集時にエラーにする。E2E（`e2e/steps/`）と component（`tests/component-steps/`）で実装は別だが、文言の規約は共通（同じ文は層をまたいで同じ意味。例:「都市マーカー『バビロン』が表示されている」は E2E では実ページ上のマーカーを、component ではモックした地図のマーカーを検証する）
- **check-specs（CI）** — ①層値が既知集合（e2e 系 / 結合）に含まれる ②実行行に期待がある ③`## 別層で検証` のポインタ先ファイルが存在する ④表が期待・層列の欠落で無言のうちに落ちていない。参照切れと構造崩れを機械が潰し、人間のレビューは「観点に漏れがないか」「各行の期待が妥当か」に絞られる
- **unit（当面）** — 既存の test.each・直接テストは観点表の行からポインタで参照する。束縛が弱い（ポインタのみ）ことは受容し、将来 unit 行も表から実行する拡張余地を残す
- **振る舞いでない検査**（構造・モック内部の検証。例: fitBounds 呼び出し）は `## 別層で検証` にポインタで可視化する。数を増やさない

## 人間のレビュー

- **毎回（唯一の定常ゲート）**: `specs/<機能>.md` の diff。観点の抜け・期待の正しさ・層の振り分け・別層/対象外の判断をここで確定する
- **語彙の増減時のみ**: フレーズ実装の diff。見る点は 3 つ — 文と実装の意味の一致 / ロケータ・クエリが正しい対象を指しているか / 否定形・待機の実装
- テストコード本体（ランナー・unit・直接テスト）は定常の精読対象にしない

## 定常フロー（機能を追加・変更するたび）

1. AI が GUIDELINE に従い、`specs/<機能>.md` を差分更新する
2. 人間が観点表の diff をレビューする
3. 機械検査: フレーズの束縛（テスト収集）+ `check-specs`（層・期待・ポインタ）
4. CI で全テストを実行する

新しい UI 操作・検証が必要になったときだけフレーズ実装を追加し、その diff を人間が検収する。

## 採用しない案

- **観点表 → Gherkin → 実行** — 観点表と .feature の二重成果物になり、間の変換（AI）を担保する仕組みがない。人間が両方をレビューするならレビューの重複、しないなら無担保
- **観点表 → テストコードを AI 生成** — レビュー済みの表と実行されるコードの間に無担保の生成が挟まり、結局コードのレビューが必要になる
- **直積網羅の機械検査** — 状態変数の値域を辞書として宣言すれば組み合わせの網羅を機械で照合できるが、辞書と値↔フレーズの間接参照を表に持ち込むことになり、人間が 1 行を読む負荷が上がる。網羅は観点の `A × B` ラベルの目視に委ね、表は実行フレーズを直接書くフラットな 1 形式に保つ
