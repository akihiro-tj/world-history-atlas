# テスト戦略 設計スペック

世界史マップのテスト戦略。AI がテストコードを書き、人間のレビューを仕様の判断に集中させる前提で、テスト仕様を「実行可能な観点表」に一本化する。観点表は人間がレビューする唯一の一次情報であり、**そのまま実行される**（仕様からテストへの変換・生成の工程が存在しない）。

- 作成日: 2026-07-13
- ステータス: ドラフト（レビュー待ち）

## 目的

1. 回帰検出の網を、人間がテストコードを読まなくても信頼できる形で維持する
2. 人間のレビューを「何を検証すべきか」の判断に集中させる。全レイヤのテストケースの過不足を、観点表のレビューだけで確認できる状態を作る
3. テスト観点の抜け漏れを、勘ではなく枠（軸の直積）で防ぐ

## 基本原則

- **観点表 = 実行される仕様** — 観点表のセルはフレーズ（ステップ語彙）で書き、ランナーが表をパースして 1 行 = 1 テストとして実行する。レビューした成果物と実行される成果物が同一なので、変換の忠実性という問題がそもそも発生しない
- **フレーズと実装の機械的束縛** — 語彙にないフレーズはテスト収集時にエラーになる。信頼の土台はフレーズ実装（少数・安定）に集約され、行が何行に増えてもレビュー対象はフレーズ数に留まる
- **二重テスト禁止** — 同じ振る舞いを 2 層で検証しない
- **層の境界は技術基準のみ** — E2E = jsdom で原理的に検証できないもの(実 MapLibre の描画・実ビューポートのレイアウト・実ブラウザのリロード往復)/ component = 結合でしか確認できないもの（画面の状態遷移・モジュール連携。地図はモック）/ unit = 純ロジック
- MSW は使わない。静的 JSON 取得のみのアプリで、fetch 境界は unit が網羅している

## 成果物と配置

```
specs/
  GUIDELINE.md            観点導出・表の書式・フレーズ語彙の運用（全レイヤ対象）
  <機能>.md               実行可能な観点表（機能ごと 1 ファイル。唯一の一次情報）
tests/
  spec-runner/            表のパースとフレーズのディスパッチ（共有ライブラリ、純ロジック）
  component-steps/        component 用フレーズ実装（Testing Library + モック）
  component.spec.ts       Vitest エントリ（specs/*.md の c 行を実行）
e2e/
  steps/                  E2E 用フレーズ実装（Playwright）
  catalog.spec.ts         Playwright エントリ（specs/*.md の e2e 行を実行)
src/**/*.test.{ts,tsx}    unit・直接テスト（観点表からポインタで参照）
scripts/check-specs.ts    枠の網羅・参照整合の機械検査（CI）
```

playwright-bdd・Gherkin ランナーなどの外部フレームワークは使わない。ランナーは素の Playwright / Vitest の上の薄いパーサ + ディスパッチ（数百行）で、リポジトリが所有する。

## 観点表の書式

すべての表は **状態（Given）→ 操作（When）→ 期待（Then）を左から右に読む**。列の役割を見出しに書くことで「どう読むか」を表自体に持たせる。フレーズ（長文）を状態・操作の列に置くと枠の構造が埋もれるため、相互作用のグリッドでは軸の値を短い列に置き、フレーズは軸の辞書へ追い出す。

### 軸と、値 → フレーズの辞書

軸マトリクス表で使う軸は「軸」表で値域を宣言し、同時に各値を実行フレーズへ対応づける（フレーズ列）。この対応は機能ごとに一度だけ書き、一度だけレビューする。

| 軸 | 値 | フレーズ |
| --- | --- | --- |
| 選択中のフィーチャー | なし | |
| 選択中のフィーチャー | ★2都市 | 都市マーカー「ウル」を選択している |

直積の網羅検査だけに使う軸（辞書が不要な軸）は 2 列（軸 / 値）でよい。

### 2 つの表形式

- **軸マトリクス表** — 相互作用のグリッド。見出しは `## A × B`、列は `# | 状態（A） | 操作（B） | 期待 | 層 | 備考`。状態・操作の列には軸の**値だけ**を書き、値の並びで MECE を縦に確認できる。ランナーは各値を辞書でフレーズに解決する
- **単発表** — グリッドにならない観点。列は `# | 観点 | 状態 | 操作 | 期待 | 層 | 備考`。状態・操作にはフレーズを直接書く。多軸の相互作用を単発表で書く場合は観点を `A × B` の組ラベルにする（直積を機械検査できる）。単軸の 2〜3 値の列挙は観点欄に並べて目視確認する

### 共通の列

- **状態 / 操作** — Given / When。マトリクスは軸の値（辞書で解決）、単発はフレーズ（`<br>` 区切り）。空欄可
- **期待** — Then。フレーズ（`<br>` 区切り）。実行行（e2e / c）は必須
- **層** — `e2e` / `e2e(smoke)` / `e2e(mobile)` / `c` / `unit` / `直接` / `=N`（同じ表の N 行と同値。理由を備考に）/ `対象外`（理由を備考に）
- **備考** — 同値・対象外の理由、unit・直接のポインタ、`前置き: フレーズ`（その行だけの追加準備）

実行順は 前提 → 前置き → 状態 → 操作 → 期待。`前提:` は表の直前に置く共通フレーズ。

## 束縛と検査（忠実性の設計）

- **フレーズ ↔ 実装** — ランナーは登録済みフレーズ（正規表現）にマッチしないセルをテスト収集時にエラーにする。E2E（`e2e/steps/`）と component（`tests/component-steps/`）で実装は別だが、文言の規約は共通（同じ文は同じ意味。例:「テーマ一覧の取得が失敗する状態である」は E2E ではルート遮断、component ではモック）
- **check-specs（CI）** — ①`A × B` 表が直積を網羅している（軸マトリクスは値の列を、単発表は観点の組ラベルを照合）②実行行に期待がある ③`=N` の参照先が存在する ④unit・直接のポインタ先ファイルが存在する ⑤層の記法と、マトリクスのセル値が軸宣言に整合する。「枠の網羅」と「参照切れ」を機械が潰し、人間のレビューは「軸の値域に漏れがないか」「各行の期待と同値判断が妥当か」に絞られる
- **unit（当面）** — 既存の test.each・直接テストは観点表の行からポインタで参照する。束縛が弱い（ポインタのみ）ことは受容し、将来 unit 行も表から実行する拡張余地を残す
- **振る舞いでない検査**（構造・モック内部の検証。例: fitBounds 呼び出し）は `直接` としてポインタで可視化する。数を増やさない

## 人間のレビュー

- **毎回（唯一の定常ゲート）**: `specs/<機能>.md` の diff。観点の抜け（軸と枠）・期待の正しさ・層の振り分け・同値と対象外の判断をここで確定する
- **語彙の増減時のみ**: フレーズ実装の diff。見る点は 3 つ — 文と実装の意味の一致 / ロケータ・クエリが正しい対象を指しているか / 否定形・待機の実装
- テストコード本体（ランナー・unit・直接テスト）は定常の精読対象にしない

## 定常フロー（機能を追加・変更するたび）

1. AI が GUIDELINE に従い、`specs/<機能>.md` を差分更新する
2. 人間が観点表の diff をレビューする
3. 機械検査: フレーズの束縛（テスト収集）+ `check-specs`（枠の網羅・参照整合）
4. CI で全テストを実行する

新しい UI 操作・検証が必要になったときだけフレーズ実装を追加し、その diff を人間が検収する。

## 採用しない案

- **観点表 → Gherkin → 実行** — 観点表と .feature の二重成果物になり、間の変換（AI）を担保する仕組みがない。人間が両方をレビューするならレビューの重複、しないなら無担保
- **観点表 → テストコードを AI 生成** — レビュー済みの表と実行されるコードの間に無担保の生成が挟まり、結局コードのレビューが必要になる
- **Gherkin（.feature）を一次情報にする** — 枠（軸 × 直積）と「対象外・同値」の判断を表現する語彙がなく、観点の完全性レビューが構造化できない

## 移行方針

1. spec-runner（表パース + フレーズディスパッチ）を実装する。パーサは純ロジックとして unit テストを書く
2. `specs/GUIDELINE.md` と `specs/<機能>.md`（7 機能）を作成する。現行 E2E 20 シナリオは技術基準で仕分けて行に変換し、技術基準に該当しないものは c 行にする
3. E2E を表実行へ切り替える（`e2e/catalog.spec.ts` + フレーズ実装。playwright-bdd / bddgen は撤去）
4. component のフレーズ実装とモック基盤を作り、既存の結合的テスト（App.test.tsx のフロー）を c 行として移行する。fitBounds・競合応答の 2 件は直接テストとして残す
5. unit は移行せず、観点表からポインタで参照する
6. `check-specs` を実装して CI に載せる
7. CLAUDE.md・README を新しい運用へ更新する
